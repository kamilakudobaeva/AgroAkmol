## 1. Что делаем

MVP закрывает задачи **2.1 (прогноз урожайности) + 2.2 (риск засухи/суховея/раннего
снега по декадам с уведомлениями)**. 2.3 и 2.4 — как endpoint'ы v2, если останется время
(архитектура их не блокирует).

Формат: **мобильное приложение (Flutter, iOS+Android)** + **бэкенд FastAPI (Python)**
с ML-моделью и AI-чатом поверх неё.

## 2. Источники данных (реальные, под Акмолинскую область)

| Данные | Источник | Примечание |
|---|---|---|
| Урожайность/валовый сбор по культурам, по годам | `stat.gov.kz/ru/region/akmola/dynamic-tables/1485/` (Бюро нацстатистики РК) | Таблицы "Урожайность основных с/х культур", "Валовый сбор", "Уточненная посевная площадь". | Границы/районы области | Список районов Акмолинской области (Аккольский, Аршалынский, Астраханский, Атбасарский, Буландынский, Бурабайский, Егиндыкольский, Ерейментауский, Есильский, Жаксынский, Жаркаинский, Зерендинский, Коргалжынский, Сандыктауский, Целиноградский, Шортандинский) | Заменяет `state/district` из индийской версии |

## 3. Индекс риска (2.2) — формула для decadal risk score

Для каждой декады (10 дней) сезона считаем три под-индекса, 0–100:

- **Засуха**: дефицит осадков декады относительно многолетней декадной нормы (Open-Meteo/NASA POWER history) + `GWETROOT` (влажность почвы, NASA POWER) ниже порога.
- **Суховей**: доля дней в декаде, где одновременно `T2M > 25°C`, `RH2M < 30%`, `WS2M > 5 м/с` (стандартное метеоопределение суховея).
- **Ранний снег/заморозок**: смещение даты первого заморозка (`T2M_MIN < 0°C`) в текущем сезоне относительно медианы за N лет.

Итоговый `risk_score = max(засуха, суховей, заморозок)` по декаде + отдельный breakdown по трём компонентам. Порог для push-уведомления — настраиваемый (по умолчанию `risk_score > 65`).

## 4. API-контракт (обязателен для всех — это то, что всех соединяет)

**Зафиксированные форматы значений** (согласовано между мобильным приложением
от Gemini и AI-слоем от DeepSeek — ML-пайплайн от ChatGPT должен отдавать
данные именно в этом виде):

- `risk_score`, `drought`, `sukhovei`, `frost` — float в диапазоне **0.0–1.0**
  (не 0–100; мобильное приложение само умножает на 100 для отображения %).
- `direction` в `top_factors` — строго **`"up"` или `"down"`** (без `"neutral"` —
  мобильное приложение ждёт ровно эти два значения).
- `impact` в `top_factors` — абсолютный вклад фактора в **т/га** (в тех же
  единицах, что и `yield_t_ha`), а не относительная доля/проценты. Мобильное
  приложение показывает его как `%` от прогноза — при сборке поправить это на
  «±X т/га», либо пересчитывать `impact/yield_t_ha*100` на клиенте.
- `yield_t_ha` и `confidence_interval` — **тонны/га** (не центнеры/га) во всех
  текстах объяснений и промптах, включая AI-чат.

```
POST /fields
  body: { name, district, latitude, longitude, crop, area_ha }
  → { field_id }

GET /predict/{field_id}
  → {
      yield_t_ha: float,
      confidence_interval: [low, high],
      top_factors: [ { name, impact, direction } ],   // из SHAP
      season: string
    }

GET /risk/{field_id}
  → {
      decades: [
        { decade_label, risk_score, drought, sukhovei, frost, note }
      ],
      alert: bool
    }

POST /chat
  body: { field_id, message, history? }
  → { reply, used_context: {yield_prediction, risk_summary} }
```

Все три исполнителя (мобильный UI, ML-пайплайн, AI-чат) работают строго против этой
схемы — это гарантирует, что их куски соберутся без ручной переделки контрактов.

## 6. Как собрать всё воедино

1. Скачайте вручную xlsx с `stat.gov.kz` (раздел 2) → `data/raw/government/`.
2. Пришлите мне то, что вернут Gemini/ChatGPT/DeepSeek (код или архивы) — я разложу
   по структуре `src/crop_yield_prediction/`, `mobile/`, проверю совместимость с
   контрактом из раздела 4 и поправлю, где не сойдётся.
3. Финальная сборка: `make bootstrap && make train && make api` (бэкенд) +
   `flutter run` (мобильное приложение).
